Every request needs a plan check.

Stub answers from memory, asks the billing provider only when it has to, and stays closed when the answer matters.

Pick a route and press the arrow.

The whole check.
No slowdown.

A plan check is a lookup, and a lookup costs a network call. Stub keeps that call off the path of almost every request.

The token is checked on your server
Stub checks the signature, the issuer and the expiry with stored public keys. A request makes no network call for this step.
Plans are kept in memory
An answer is fresh for 30 seconds. After that it is stale, and Stub serves it at once while a refresh runs behind the request.
Many requests share one lookup
If 200 requests ask about the same new customer, Stub makes one call and gives the answer to all of them.
A plan change clears the answer
When the billing provider reports a plan change, Stub forgets that customer. The next request asks again.
It stays closed when it matters
If the plan cannot be checked, a cheap route lets the request through. A sensitive route returns 503.

Where does each answer come from?

Every response carries a stub-source header, so you can see which of the four cases you got.

freshYounger than 30 seconds. Stub uses it as it is.

Frequently
asked questions

Why not put the plan in the token?
The Kinde docs list no billing entitlements claim, and a token lives 24 hours by default. A plan in the token would be as old as the token.
How wrong can the answer be?
Up to about 30 seconds after a plan change, or until the change event arrives. While the provider is down, up to 5 minutes.
Does it need Kinde?
No. The gateway needs a way to check a signed token and a way to read a plan. This version uses Kinde, and the stand-in runs with no account.
Should it fail open or closed?
That depends on the route. Fail open where a wrong yes is cheap. Fail closed where it is not.
